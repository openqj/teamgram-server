# 版本与发布

本文档约定版本号规则、CHANGELOG 格式及发布检查清单。

## 版本号规则

- 采用**语义化版本**思想，格式示例：`v0.96.0-teamgram-server`。
  - **主版本号**：不兼容的 API 或架构变更。
  - **次版本号**：向后兼容的功能新增。
  - **修订号**：向后兼容的问题修复与小改进。
- 后缀（如 `-teamgram-server`）可用于与依赖库（如 proto）区分。

## CHANGELOG

- **位置**：仓库根目录 **CHANGELOG.md**（若已创建）。
- **格式**：推荐 [Keep a Changelog](https://keepachangelog.com/)（按版本分段：Added / Changed / Deprecated / Removed / Fixed / Security）。
- **责任**：每次发布前更新 CHANGELOG，将本次改动归入对应版本与类型。

## 生产上线验收

生产上线或变更关键路径前，为该版本记录以下证据。功能状态以 [Layer 229 唯一方法台账](../LAYER229_METHOD_LEDGER.csv)为准，性能目标和测量边界以[架构文档](architecture-zh.md)为准，阶段依赖见[路线图](roadmap-zh.md)。

1. **功能与协议**：支持客户端所需方法的 TL 合约、权限、幂等性、业务结果、持久化和多设备更新达到台账规定的生产验收状态。单会话成功、正确 constructor 或编译通过不足以证明完整功能上线就绪。
2. **数据库切换**：切换 PostgreSQL 默认运行路径前，schema、DAO、原始 SQL、初始化/迁移、所有生产服务及 Layer 229 探针在 PostgreSQL 18 上通过；明确持久化与更新/Outbox 的事务边界，避免保留长期双数据库生产路径。
3. **故障与恢复**：验证断线差分补齐、投递失败重试、重复事件、进程退出、Worker 中断、权限变化及主库故障。按明确的故障模型记录已确认消息与更新的恢复结果、备份恢复演练以及对应 RPO/RTO；异步副本不能作为主库故障零数据损失的证据。
4. **性能与容量**：固定在线人数、消息/广播速率、群/频道规模、媒体并发、历史数据量、缓存冷热、地区/RTT、硬件及复制配置，记录各场景的 P95/P99、吞吐、CPU/内存、数据库锁等待、队列积压和恢复追赶时间。50/300/100 ms 初始预算须在选定负载下验证，不能作为已达成性能或 Telegram 官方指标发布。
5. **媒体与外部依赖**：配置并验收所需的真实授权、通知推送、对象存储和其他 provider。通话范围内须验证与客户端匹配的信令、TURN/中继、SFU、双向音视频及重连；后台媒体任务和通话结束后有资源释放证据。
6. **部署与回退**：验证会话节点退出后的恢复、内部 RPC/基础设施的网络边界、监控告警和发布恢复路径。逐模块独立化变更须有兼容性与性能证据，以及可回退或兼容迁移方案。

这些是验收要求，文档记录不自动提升方法状态，也不表示当前版本已完成 PostgreSQL 迁移或达到上述性能预算。

## 发布检查清单

发布新版本时建议完成：

1. **版本号**：在 Makefile 或版本注入处更新 `VERSION`（若适用）。
2. **CHANGELOG**：在 CHANGELOG.md 中新增该版本条目并填写变更摘要。
3. **Tag**：在 Git 中打 tag（如 `v0.96.0`）并推送到远程。
4. **二进制/镜像**：按项目惯例构建并发布预编译二进制或 Docker 镜像。
5. **README**：若主 README 中有固定版本号或“当前版本”说明，按需更新。
